## 1. Краткое описание проекта

Проект представляет собой Telegram-бота для закрытого домового чата.

Бот предназначен для того, чтобы пускать в чат только реальных жильцов дома.

Основная задача бота:

- принять пользователя в личке;
- провести регистрацию;
- собрать анкету;
- принять фото-подтверждение проживания;
- отправить заявку администратору;
- дать администратору возможность принять решение;
- после решения администратора разрешить или отклонить доступ.

### 2.1. Фактически реализовано в текущем коде

На текущий момент в проекте уже реализовано следующее:

- Telegram-бот на `pyTelegramBotAPI` с точкой входа в `main.py`.
- Загрузка конфигурации из `.env` и поддержка proxy для Telegram API через `HTTP_PROXY` / `HTTPS_PROXY`.
- Автосоздание SQLite-таблиц `houses`, `users`, `cars`, `applications`, `admin_actions` при старте.
- Основной пользовательский вход через `/start` в личке с ботом.
- Альтернативный вход через `/newuser`.
- Пошаговая регистрация пользователя:
  - имя;
  - фамилия;
  - квартира;
  - телефон;
  - автомобили.
- Проверка телефона через `phonenumbers`.
- Сбор фото от пользователя и отправка его администратору вместе с анкетой.
- Админские действия через inline-кнопки:
  - разрешить доступ;
  - отклонить доступ;
  - запросить новое фото.
- Проверка пользователей по конкретному дому через `/check`.
- Сводка по всем домам через `/checkall`.
- Заявки на доступ и решения администратора сохраняются в таблицы `applications` и `admin_actions`.
- Веб-панель `webapp/app.py` (отдельный сервис `residentchatbot-web.service`): сводка, заявки и история решений, только чтение; все страницы с данными жильцов закрыты HTTP Basic auth, публичен только `/health`.
- Обработка выхода пользователя из чата и обновление данных в БД.
- Формирование предложения пользователю подтвердить регистрацию и обработка отказа.
- Защита от падения на временной сетевой ошибке при `polling` через retry-цикл.
- В репозитории уже есть `README.md` с текущими командами запуска и ручным flow-check, а также `.env.example` с безопасным шаблоном переменных.

### 2.3. Что работает, но остаётся хрупким

Эти части нельзя ломать, но их нужно постепенно стабилизировать:

- Состояния регистрации частично живут в памяти, а не в базе данных.
- Логика сильно смешана: SQL, Telegram-обработчики и бизнес-правила находятся в одних и тех же файлах.
- В `main.py` и `registration.py` много прямых обращений к БД внутри handlers.
- Есть зависимость от текущего порядка событий и от того, что сервис не перезапустился в середине пользовательского flow.
- Есть дублирующиеся или пересекающиеся сценарии подтверждения регистрации.
- Есть места, где логика опирается на `tg_id` и `house`, и это нужно аккуратно нормализовать дальше.
- Локальная in-memory модель состояний и прямой SQL в handlers делают поведение чувствительным к рестартам и будущим изменениям схемы.

## 3. Важное production-уточнение

Бот уже работает на сервере.

Это означает:

1. Нельзя переписывать проект с нуля.
2. Нельзя сразу делать большой рефакторинг.
3. Нельзя менять схему БД без бэкапа и миграции.
4. Нельзя ломать текущий пользовательский сценарий.
5. Нельзя ломать admin callback-кнопки.
6. Нельзя менять `.env`-переменные без обратной совместимости.
7. Нельзя менять systemd-запуск без отдельного решения.
8. Нельзя менять proxy-настройки без отдельного решения.
9. Перед изменениями нужно понимать, как откатиться назад.

Любая доработка должна идти по принципу:

> Сначала зафиксировать, потом сделать бэкап, потом менять маленькими шагами, потом проверять, потом обновлять этот файл.

## 6. Пользовательский сценарий

Пользователь открывает личный чат с ботом и отправляет `/start`.

Бот должен:

1. Поприветствовать пользователя.
2. Объяснить назначение бота.
3. Запустить регистрацию.
4. Пошагово запросить:
   - имя;
   - фамилию;
   - номер квартиры;
   - телефон;
   - автомобили;
   - фото из окна квартиры или другое фото-подтверждение проживания.
5. Проверить корректность введённых данных.
6. Сохранить заявку.
7. Отправить заявку администратору.
8. Сообщить пользователю, что заявка отправлена на проверку.
9. После решения администратора уведомить пользователя о результате.

## 7. Админский сценарий

Администратор получает заявку пользователя.

В заявке должны быть видны:

- имя;
- фамилия;
- квартира;
- телефон;
- автомобили;
- дом;
- Telegram username;
- Telegram ID;
- фото-подтверждение;
- текущий статус заявки.

Администратор должен иметь действия:

- `Разрешить доступ`
- `Отклонить`
- `Запросить новое фото`

После решения администратора бот должен:

- обновить статус пользователя;
- сохранить решение;
- уведомить пользователя;
- при необходимости уведомить администратора;
- не ломаться при повторном нажатии на кнопку.

## 8. Рекомендуемые статусы пользователя

Нужно постепенно формализовать статусы.

Рекомендуемые статусы:

- `new` — пользователь начал взаимодействие;
- `registration_in_progress` — регистрация идёт;
- `photo_required` — ожидается фото;
- `pending_review` — заявка отправлена администратору;
- `photo_requested_again` — администратор запросил новое фото;
- `approved` — доступ разрешён;
- `denied` — доступ отклонён;
- `blocked` — пользователь заблокирован;
- `left_chat` — пользователь вышел из чата, если такая логика будет добавлена позже.

Статусы должны храниться в базе данных.

Требования:

1. Сохранить поддержку `HTTP_PROXY` и `HTTPS_PROXY`.

## 15. Systemd

Проект уже работает на сервере через `systemd`.

Codex должен сначала найти и описать фактический systemd unit.

Рекомендуемые команды проверки:

```bash
systemctl status <service-name>
journalctl -u <service-name> -n 100 --no-pager
```

Пример unit-файла:

```ini
[Unit]
Description=House Chat Telegram Bot
After=network.target

[Service]
WorkingDirectory=/opt/house-chat-bot
ExecStart=/opt/house-chat-bot/venv/bin/python main.py
Restart=always
RestartSec=5
EnvironmentFile=/opt/house-chat-bot/.env

[Install]
WantedBy=multi-user.target
```

Фактический unit может отличаться.  
Перед изменениями нужно зафиксировать реальное состояние сервера.

```bash
git status
```

```bash
systemctl stop <service-name>
```

## 30. Версионирование и релизы

Это обязательные требования для дальнейшей работы с проектом.

### 30.1. Источники истины

- `PROJECT_SPEC.md` - живой план, baseline проекта, текущий статус этапов и progress log.
- `CHANGELOG.md` - история релизных изменений и заметных пользовательских или операционных изменений.
- git-теги - фиксация релизных точек и стабильных baseline-версий.

### 30.2. Схема версий

- Используется `semver`: `MAJOR.MINOR.PATCH`.
- `PATCH` - багфиксы и безопасные изменения без ломки пользовательского flow.
- `MINOR` - новые возможности и улучшения, не ломающие обратную совместимость.
- `MAJOR` - только для ломающих изменений, которые требуют отдельного решения и, как правило, миграции.

### 30.3. Правила релизов

- Каждый релиз должен быть отражён в `CHANGELOG.md`.
- Каждый релиз должен иметь git-тег вида `vMAJOR.MINOR.PATCH`.
- `Unreleased` в `CHANGELOG.md` используется для текущих незавершённых изменений.
- `PROJECT_SPEC.md` не заменяет `CHANGELOG.md` и не должен использоваться как релизный журнал.
- `CHANGELOG.md` не заменяет `PROJECT_SPEC.md` и не должен использоваться как план работ.
- Короткая команда вида `запушь PATCH`, `запушь MINOR`, `запушь MAJOR` или `запушь vX.Y.Z` означает: выбрать релизную версию по `semver`, обновить релизную документацию при необходимости, поставить git-тег и запушить его в `origin`.

### 30.4. Текущий baseline

- Текущий baseline проекта фиксируется тегом `v0.3.0` (веб-панель, журнал заявок и решений администратора).
- Предыдущие релизы: `v0.2.0` — первый формальный релиз после исходного рабочего baseline `v0.1.0`.
- Все последующие изменения должны учитываться через `CHANGELOG.md`, а при выпуске релиза сопровождаться новым git-тегом.
